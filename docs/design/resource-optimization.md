# Resource use across the Host, kernel and clients

**Design proposal against `59889a049`.** Start with the work every native Agent conversation pays for before its first model request. The first change gives the model its selected tools and default context without starting processes that forward calls back to the Host. History reads, content collection, desktop rendering and release packaging can ship independently.

## Baseline and delivery order

| Workload | Observed baseline | What to measure after the change |
| --- | --- | --- |
| Prepare the tool directory twice in one fresh Windows extension runtime, same thread, no workspace, no tool execution | Each preparation started 11 tool broker processes. Nine providers remained pinned for 56 services, with 233–238 MiB combined private committed memory. Releasing the leases returned the broker count to zero. | Count new first-party forwarding processes in both rounds, then measure time to the first model request and private memory with concurrent Bots. |
| Prepare default context in those same two rounds | The first preparation started one context broker. The second reused the declaration cache. | Count cold and warm preparation separately. A fresh thread using the built-in guidance should also start zero context brokers. |
| Windows x64 Full Desktop 0.9.52 | 224.2 MiB installer, 859.7 MiB unpacked. These are distribution sizes. | Compare like-for-like artifacts on the same platform and list the features available offline. Measure process memory separately. |

The first two rows exercised the real broker and preparation code with isolated data. Tool configuration, available sources and selected plugins affect the result in a deployed Host. For a production memory comparison, repeat the same workload on the same processes and sample after the work settles. On Linux, record Host and kernel memory separately from the container's file cache. [Measurement guide](../performance.md)

1. Ship direct first-party tool dispatch and default context in the **first PR**, including recovery of existing tool bindings. Verify it independently in the full Host.
2. Varin 0.9.53 is the bridge for WAL-only TriviumDB 0.8 stores. Subsequent builds ship the current addon and its matching migrator.
3. Reuse verified grammars and avoid reading old message bodies for history deltas. Land and measure each on its own. Change content collection separately because it controls physical deletion.
4. Prioritize the remaining renderer, desktop, distribution and build changes by measured cost on the affected deployment.

## First-party tools and context

The Host already owns web, Office, browser, Computer Use, scripts, images, interactive UI, code exchange, research discovery, environment forwarding and runtime management. Today a built-in such as Web registers an extension callback that sends the arguments back to the same Host service. Directory preparation can activate that callback before the model has even selected a tool. [Web forwarding entrypoint](../../packages/extension-builtins/src/host/web-extension.ts) · [Tool preparation and execution](../../packages/web/application-host/lib/kernel/extension-tool-owner.ts)

### From declaration to execution

| When | Owner and action |
| --- | --- |
| Prepare the model request | The Host projects its built-in declarations using the Run's source, tool configuration and enablement. Resolve built-ins and installed contributions through the existing service routing rules, including scope, explicit selections, ambiguity and fallback. Publish the selected schemas and configuration to the kernel at the existing request boundary. |
| Select a provider | A built-in declaration resolves to its Host handler. Settings and plugins can discover the same service IDs. An explicitly selected third-party provider follows its own activation and trust contract. A plugin that supplies its declaration dynamically may need preparation. Preserve the user's choice if that provider is unavailable and apply the configured fallback rule. |
| Execute | The kernel sends the admitted operation to the existing tool bridge. Share argument validation, short-reference resolution, permission evaluation, confirmation, cancellation and result projection across Host handlers and plugin callbacks. The built-in handler calls the domain service directly. The plugin backend invokes its selected binding. |
| Complete or cancel | The domain that performed the work supplies the receipt. Preserve whether the call was dispatched, its effect and whether execution stopped. A confirmed effect survives a later error in result presentation. Release execution resources when their work settles. |

Keep one declaration and routing path for chat, settings and plugins. Factor the common invocation code out of the current extension tool owner. A Host handler can carry a lightweight binding for a prepared request without starting an OS process. Retain the public Host capabilities used by third-party extensions. Remove a forwarding capability when its last real consumer has moved. Resolve immutable launch facts once per invocation where possible. Check current permission and cancellation state when dispatching, including after the user or permission judge has taken time to respond. [Service routing](../../packages/extension-contract/src/service-routing.ts) · [Tool bridge](../../packages/web/application-host/lib/kernel/tool-bridge.ts)

### Existing Runs and upgrades

| Work at the upgrade boundary | Expected behavior |
| --- | --- |
| A root Run can prepare its next model request | Use the current selection at the next closed request boundary. Installing, disabling or replacing a tool can affect subsequent work. Preserve the history and receipts of completed calls. |
| A delegated Run inherited a fixed tool set | Recover only the services and configuration the child was granted, including an empty set. Preserve a selected third-party implementation. For a known legacy bundled provider, translate the saved binding to a compatible Host handler using its original provider and service identity, schema and configuration. Record the new implementation identity explicitly. An incompatible binding gets a specific recovery error. |
| An operation was dispatched before restart | Reconcile its original operation and receipt. An unknown external effect stays with that operation. Preparing a new handler must never cause a second dispatch of the old call. |

Today the persisted binding contains the provider key, package and service versions, artifact integrity, composition, declaration hash and configuration identity. A matching name or a `varin.builtin.` prefix alone cannot establish equivalence. Use a narrowly scoped upgrade for known bundled declarations if the durable representation changes. Keep the historical identity available on original receipts and use the real Host identity for new calls. [Binding format](../../kernel/crates/varin-runtime/src/catalog_launch.rs) · [Root and child preparation](../../packages/web/application-host/lib/kernel/agent-runtime-client.ts)

**Other first-party contributions have different dispatch rules.**

- Declare the built-in guidance in the Host. `varin.context.fragments@1` supports ordered composition. Resolve the selected sequence once and emit each member's fragments in order. A selection containing only plugins yields only those plugins' fragments. Reuse the current warm cache for unchanged declarations. [Context contract](../../packages/extension-contract/src/context-fragments.ts) · [Composition](../../packages/web/application-host/lib/kernel/context-composition.ts)
- Workspace recovery uses **`varin.workspace-recovery@7`**. Several providers may register. Each recovery call goes to exactly one selected provider. A direct built-in handler and a plugin override must never both apply the same file restoration. Ship this conversion separately with a file-and-conversation restore and undo against the selected provider. [Service identity](../../packages/extension-contract/src/services.ts) · [Recovery client](../../packages/ui/src/lib/recovery/workspaceRecovery.ts)
- Publish bundled language provider descriptors from the Host. Start the relevant language server when an editor or an explicit Host request actually needs that view. Keep unsaved editor buffers, the disk view and fixed Agent sources distinct. Ordinary Agent structural retrieval uses Tree-sitter. [Language service ownership](../../packages/web/application-host/lib/lsp/DOCUMENTATION.md)

**First PR acceptance.** Use a full Host with the default built-ins and a controlled model endpoint. Send two consecutive messages and count first-party forwarding brokers created during preparation. The target is zero in both rounds. Execute one built-in with a short reference and verify its receipt. Select a plugin for that slot and verify it alone receives the call. Cancel while confirmation is pending and verify the domain receives no call. Exercise recovery from a pre-change binding with a root, a fixed child and an already-dispatched operation. Opening a workspace and selecting custom context providers are separate workloads.

## Kernel and Host work that grows with history or file count

### Structural reads

The syntax worker currently reads and hashes the grammar WASM before consulting its language cache. Capture verified bytes by the admitted grammar hash and reuse them for subsequent files. Installed grammars already have content-addressed storage. A changed recipe selects new verified contents. Where a path can change externally, establish its identity before accepting new bytes. Matching length and modification time alone provide insufficient evidence of content identity. Keep cancellation and query invalidation at their existing boundaries. [Syntax runtime](../../kernel/crates/varin-kernel/src/compute/structure.rs) · [Grammar store](../../packages/web/application-host/lib/structure/grammar-store.ts)

Compare repeated parses of the same grammar across many source files, then replace the grammar and change the query independently. Count full grammar reads, hashes and compilations, and compare extracted symbols. The pinned Tree-sitter API loads a language from bytes into a worker's WASM store. Evaluate shared engine or compiled-module reuse separately if compilation still dominates. Profile repeated path resolution and whole-file reads during retrieval against representative large source files before changing supported inputs.

### History deltas and live receipts

The history head identifies messages. A queued input, completed background operation, model selection or failure can change while that head stays the same. Today the kernel hydrates the recent message window before it selects the delta, partly to find references to tool operations. [Thread view](../../kernel/crates/varin-runtime/src/catalog_thread_view.rs)

Record the model request and operation references needed by the view alongside new history entries, in the same commit. Include accepted jobs, effectful tool results and policy tool outputs, preserving observer semantics. Traverse window metadata to find the cut and collect its receipt references. Hydrate text and model presentation only for messages actually returned. Read the other live parts of the view from their owners. Preserve the existing full-window response for an unknown cut.

Old histories need the same reference information. Populate it from their original entries during a format upgrade or on first access to an unindexed window. Distinguish an indexed entry with no references from one still awaiting conversion. Measure cold upgrade and warm steady state separately. With an indexed window and an unchanged head, expect **zero prior message bodies loaded** and a newly settled operation still visible. Verify append, rollback, media references and cancellation during a read. [History and delta fixtures](../../kernel/crates/varin-runtime/src/catalog_thread_view.rs)

### Catalog reads, notifications and content collection

Reuse the reader's SQLite connection for work that belongs to one snapshot. Keep the epoch check at the snapshot boundary and after releasing it, including cancellation paths. Detached content reads may outlive that snapshot and need their own owner check. Select hot queries from traces and query plans. Share attention-cache entries across readers only where keys identify the same committed state and the saved reads outweigh contention. [Read snapshots](../../kernel/crates/varin-runtime/src/catalog_reads.rs) · [History reader](../../kernel/crates/varin-runtime/src/catalog_history.rs)

Event inserts already send coalesced notifications. One wake can still trigger broad reconciliation. Narrow the work by the committed changes that affect each consumer and index active managed operations if the query plan shows a scan of historical operations. Preserve recovery on startup and the wake when executor ownership actually ends. If notification delivery moves to commit, publish after a successful commit, discard rolled-back changes and test that a concurrent commit remains observable. Measure lock waits and WAL growth before changing checkpoint or busy-timeout policy. [Event notifications](../../kernel/crates/varin-runtime/src/catalog_observe.rs) · [Managed operations](../../kernel/crates/varin-runtime/src/catalog_managed_process.rs)

Content collection is a separate change. Register a reader before SQLite fixes its snapshot and protect referenced files until the last dependent content read ends. Give writers separate ownership over newly created or reused content through durable publication. Readers can then overlap root discovery and verification. Before unlinking an object, serialize the deletion decision with writers and account for readers whose older snapshot can still reach it. A writer reusing an orphan between mark and deletion invalidates that candidate or the pass. Keep the existing content hash validation when reusing objects, including a concurrent install at the same hash. A same-length damaged file must not become the target of a new committed reference.

Acceptance requires collection to make progress under repeated short reads, a reader spanning a commit to finish with the correct bytes, and orphan reuse during sweep to preserve the newly published content. A corrupt live object must still stop an unsafe sweep. [Content lifetime](../../kernel/crates/varin-runtime/src/content.rs) · [Collection](../../kernel/crates/varin-runtime/src/content_collection.rs) · [Concurrent publication cases](../../kernel/crates/varin-runtime/src/catalog_content_collection_tests.rs)

### Other Host and kernel costs

| Path | Change and behavior to verify |
| --- | --- |
| Documents and Blob transport | Separate browsing metadata from content-derived revisions, encoding and conflict checks. Read and hash bytes once where the caller needs an exact revision. Measure large transfers with binary payloads over the existing transport, including ordering, cancellation, backpressure and the final receipt. |
| Terminal, compute and filesystem workers | Count OS thread starts during typing, resize and bulk output. Route short blocking jobs to existing on-demand workers and preserve input order. Remove avoidable Base64 conversions and per-byte allocations in output paging while preserving cursors and split multibyte characters. Combine runtimes or the directory watcher only if measurement justifies changing cancellation or restart ownership. |
| Settings and network requests | Let hot consumers reuse their validated projection of the settings they need. Preserve independent editable results for existing settings-store callers, external atomic replacements and one-time uncached loads such as the model directory. File watchers may lag behind a completed external write. |
| Inference, Computer Use and knowledge stores | Acquire workers on demand and release idle execution resources after work settles. Track actual inference requests, desktop capture and input owners, knowledge reads and writes. For model replacement, drain old leases and handle load failure. Measure memory returned alongside first-use latency. Base any idle interval on those two costs. |
| PDF rendering and workspace Git discovery | Measure raster peak memory and Host event-loop stalls. Move heavy rendering off the loop and size work by the actual render requirement. Batch or overlap independent Git probes while preserving cancellation and error attribution per repository. |

Relevant entry points include [document inspection](../../packages/web/application-host/lib/documents/inspect.ts), [terminal paging](../../kernel/crates/varin-kernel/src/process/paging.rs), [settings storage](../../packages/settings-store/src/index.ts) and the [local embedder](../../packages/web/application-host/lib/knowledge/semantic/local-embedder.ts).

## Clients and desktop

**Conversation and document lifetime.** The last thread-history listener currently releases its subscription while the Host-keyed map still holds the loaded window. Once the last consumer leaves, release reconstructible items, usage and presentation data or retain a small recent working set sized from revisit measurements. Drafts, active interactive input and pending submissions have independent lifetimes. For documents, release clean buffers and edit history after the last editor, diff, save, recovery or undo owner releases its reference. A hidden tab or an unmounted virtual row can still have an owner. Reopening an evicted file must use its current revision, including after a file restore. Compare retained heap after repeatedly visiting distinct long conversations and large files, then revisit one and check reading position, drafts, undo and current file contents. [Thread history](../../packages/ui/src/lib/agent-runtime/thread-history.ts) · [Document Registry](../../packages/ui/src/lib/documents/registry.ts)

**Streaming and embedded cards.** Keep completed timeline entries stable. Project changes to the streaming assistant item and active tool independently. An ordinary text delta should cause no work proportional to the number of old interactive cards. A visible iframe needs position updates when content above it moves, including during streaming, scrolling and resize. Share layout observation at the timeline level where needed. On reconnect, refresh missed state from the committed cursor or take one fresh snapshot when the cursor is unusable. Compare typing and scrolling with zero cards and with several visible cards. [Conversation timeline](../../packages/ui/src/components/conversation/ConversationTimeline.tsx) · [Inline UI views](../../packages/ui/src/components/interactive-ui/InlineUiViews.tsx)

**Workbench and syntax highlighting.** Register the three first-party workbench views directly and load built-in settings pages when opened. Keep extension shell and navigation slots. A failed or interrupted switch must leave a usable view and preserve drafts, open documents and the selected session. Built-in views can reuse their state across the transition. Third-party replacements keep their readiness handshake. [Shell transitions](../../packages/ui/src/lib/extensions/workbench-shell-transition.ts)

Monaco serves desktop workbench editing and editable diffs. CodeMirror serves the composer, mobile and embedded editors. Pierre serves read-only diffs. The Plan editor already shares the Markdown Shiki worker with chat. Inspect the packaged module graphs for main, Mini-Chat, mobile and each worker before choosing how to deduplicate grammar and WASM assets. Shared immutable assets can reduce distribution bytes while allowing a large diff and a chat code block to execute independently. Measure a text-only chat, first highlighted block and large diff separately. Keep the composer usable at first paint. Apply the same first-use check to the file-type SVG sprite and locale bundles, including fallback text for missing translations. [Monaco](../../packages/ui/src/lib/monaco/DOCUMENTATION.md) · [CodeMirror highlighting](../../packages/ui/src/lib/codemirror/shikiHighlight.ts) · [Diff worker](../../packages/ui/src/lib/diff/workerFactory.ts)

**Desktop behavior determines which processes and windows to keep.**

- For the companion, replace full-canvas pixel readback on each new drawing with reusable alpha hit data from the artwork. Validate transparent-edge click-through, visible-edge dragging, multi-display scaling and frame timing. The stool stays at its original screen coordinates while the character moves. Compare compositions that preserve that behavior and stacking without each transition paying for a fresh renderer. [Hit testing](../../packages/ui/src/components/companion/useCompanionWindow.ts) · [Stool geometry](../../packages/electron/companion-stool.ts)
- For the embedded browser, track panel attachment, user-retained pages, thread ownership and in-flight automation separately. Throttle parked, idle pages and resume before an operation that needs an active surface. Release transient pages when their owners finish. Keep user-retained tabs accessible after closing the panel. Retire obsolete element references with their document, frame or snapshot lifetime. Verify a long-lived single-page app, reuse of a previous valid reference, capture from a hidden page and explicit tab close. [Electron browser owner](../../packages/electron/browser-owner.ts)
- Evaluate a separate Electron utility process for the embedded Full Desktop Host against menu/input latency, startup time and combined memory. Electron Main owns windows, the browser surface, desktop network session and native controls. A split needs a bridge for these operations, cancellation and shutdown, including a cancelled quit. Compare it with moving the measured blocking work off the main loop. Preserve bootstrap order and first paint if changing synchronous preload calls. ## Distribution and upgrades

The local **Windows x64 v0.9.52 Full Desktop** installer measured **224.2 MiB** and its unpacked application **859.7 MiB**. Use the same role, platform and build type for size comparisons. Report installer bytes, installed bytes, first-use download and memory loaded by an active capability separately.

Full Desktop can run the local Host. Light Desktop connects to a Host. Docker has a main service, a toolbelt profile and a resource-node image. Put each component on the device that executes the relevant service. A remote workspace alone does not imply that speech or embedding runs on that device. The existing resource node exposes a limited set of services. Offer component management there only for capabilities that node actually implements. Desktop, Web, mobile and Agent discovery should read availability and install progress from that same owner. [Desktop editions](../../packages/electron/README.md) · [Resource-node entrypoint](../../packages/web/application-host/resource-node.ts)

| Capability | Distribution decision |
| --- | --- |
| Chat, Bots, groups, file operations, search, terminal, Git and common documents | Keep the core working on a fresh Full installation. Preserve basic PDF reading. Evaluate the heavy raster backend separately with text PDFs, scanned pages and a headless Host. |
| Structural code retrieval and language intelligence | Keep core grammar assets available for structural reads. Offer heavier language servers per language on the device that serves that view. Reuse the existing language preparation flow. Support advance preparation and offline import, and allow toolbelt images to preinstall the needed programs. |
| Local embeddings and speech | Reuse the semantic component downloader and offline import. Speech models already download separately. Evaluate bundling the speech engine with its optional component using installed size and time to first transcription. Keep a previously installed, usable version available if a new download fails. |
| Extension source compilation | Account for runtime compilation of installed source extensions as well as CLI builds. Remove the bundled compiler only when those users can prepare it on the executing Host and packaged extensions that already have executable entrypoints still work offline. |

Deployment checks should include Light Desktop or mobile connected to a remote Host, and a headless Host using an isolated workspace node. Start, cancel and retry a component download on the appropriate device, then exercise the feature from a different client. [Language preparation](../../packages/web/application-host/lib/lsp/managed-servers.ts) · [Semantic components](../../packages/web/application-host/lib/knowledge/semantic/local-component.ts) · [Extension artifacts](../../packages/extension-host/src/artifact-store.ts)

### Retire the TriviumDB 0.8 helper

**Varin v0.9.53 is the last bridge release.** Its 0.8 helper produces a first complete checkpoint for stores whose acknowledged writes exist only in the write-ahead log (WAL). Each database migrates when opened, so a dormant Bot or an old backup may still need this step. [Database opener](../../packages/web/application-host/lib/knowledge/database.ts)

The 0.9.3 storage worker opens with the current engine first. When the main file is missing and only a v3 WAL remains, the error identifies the file and directs the operator to open a writable copy under Varin 0.9.53. All checkpointed stores continue through the standard migration path. [Cold backup and isolated copies](../ops/cold-backup.md)

| Sample observed with the current engine | Result to preserve after removing the helper |
| --- | --- |
| 0.8 database with only a v3 WAL and no base checkpoint | Report the v0.9.53 conversion path. Leave the original files intact. Verify the converted copy opens with its data. |
| 0.8 database with a valid checkpoint and pending v3 WAL | Open normally and recover committed entries and links. |
| Damaged main file with a v3 WAL | Report the original corruption. The WAL header is identical in all three samples. |

The old addon and its Windows loader patch have been removed from the runtime. Fixed file groups exercise direct migration, the WAL-only guidance, corruption, and the result of opening the same WAL in Varin 0.9.53. [Database fixtures and tests](../../packages/web/application-host/lib/knowledge/database.native.test.ts) · [Desktop native preparation](../../packages/electron/scripts/prepare-trivium-runtime.mjs)

## Build footprint and module ownership

Measure Rust debug symbols, incremental outputs and duplicate integration-test link products per target. Compare profiles on a clean build and an incremental rebuild, including link time and the usefulness of crash traces. Group integration binaries where fixtures and process isolation permit it. Keep internal unit tests alongside the private code they exercise. For release size, compare stripping and thin LTO on the shipped binaries for each target.

The development Host runs from a private generation named for the **running development Host PID**. Its build subprocess has a different PID. Production staging directories use the builder's PID. Reclaim abandoned generations after verifying the corresponding owner has exited. Exercise two simultaneous builds and a running watch session while recovering the directory left by a killed Host. Check the contents of release artifacts separately from untracked developer leftovers. [Development launcher](../../packages/web/scripts/run-application-host-dev.mjs) · [Host build](../../packages/web/scripts/build-application-host.mjs)

Split modules where ownership changes during this work. The Host tool registration can move with the first-party handlers. A Catalog reader can own pooled snapshots as those reads move. Electron's browser and computer callbacks define the desktop integration boundary. UI preferences and per-window transient state can have separate subscribers. Preserve dependency order when draining services, especially where active work still needs its kernel or storage owner. Promote each shipped behavior into its domain guide and retire the corresponding part of this proposal.
